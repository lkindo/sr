# 모바일 업무 흐름 검증

검증일: 2026-09-19. 로컬 개발 서버와 로컬 DB에서 기존 시드 계정의 실제 역할을 확인한 뒤 수행했다. 화면 조작으로 SR을 생성·처리하고 저장 결과를 다시 조회했다. 이번 실행에서 생성한 `MOBILE-E2E-` 요청만 ID와 제목을 대조한 후 삭제 API(소프트 삭제)로 정리한다. 해당 요청의 미발송 이메일도 명시적 ID·고유 실행 표식·생성 시각·로컬 DB 여부를 검증한 뒤 정리한다. 기존 SR·사용자·고객사 설정은 변경하지 않는다.

## 실행 환경과 재현

- Chromium / Pixel 7: 393×851, 터치·모바일 UA.
- WebKit / iPhone 13: 390×844, 터치·모바일 UA.
- 주간·야간 모드. 작은 화면 320×568, 가로 844×390, 높이 축소 390×360 추가 점검.
- Service Worker를 활성한 상태에서 재방문을 검증한다. 인증 정보를 포함할 수 있는 trace는 저장하지 않는다.
- `pnpm test:e2e:mobile` — 독립 설정 `playwright.mobile.config.ts`, 포트 3100, `TEST_MODE=true`, `PLAYWRIGHT_TEST=true`, 인증 리다이렉트도 3100으로 통일.
- 실행 전 로컬 DB 주소를 검사한다. 기존 서버는 기본적으로 재사용하지 않는다. 직접 `TEST_MODE=true`로 시작했음을 확인한 서버만 `MOBILE_E2E_REUSE_SERVER=true`로 재사용한다. 저장 직후 조회가 실패해도 실행별 표식·생성 시각으로 검증용 요청 ID를 복구해 정리한다.
- 기존 로컬 시드의 ADMIN·MANAGER·ENGINEER·CLIENT_USER·CLIENT_ADMIN 계정이 필요하다. 계정/암호를 보고서에 기록하지 않는다. 운영 DB를 연결한 서버에서는 실행하지 않는다.
- 결과: `playwright-report/mobile/index.html`, `test-results/mobile-workflow/`.

### CI 실행 구성 (2026-09-20)

`CI/CD Pipeline`의 E2E 작업은 desktop/mobile matrix로 실행하며 각 작업은 별도의 임시 PostgreSQL과 시드를 사용한다. 데스크톱은 기존 production 서버 3000, 모바일은 위 전용 설정의 개발 서버 3100에서 Chromium·WebKit 전체 16개를 실행한다. 어느 작업이 실패해도 전체 CI가 실패해 배포를 차단한다. 모바일 검증은 개발 서버 기준이며 운영 HTTPS 환경 검증과 구분한다.

`pnpm check:e2e-projects`는 서버·DB를 시작하지 않고 Playwright의 실제 수집 결과를 검사한다. 데스크톱에 모바일 스펙이 섞이거나 모바일 시나리오가 두 브라우저 중 하나에서 빠지면 실패한다. 프로젝트의 `testIgnore`가 공통 설정을 덮어써 모바일 8개가 데스크톱으로 잘못 실행되던 CI 실패를 이 검사로 재현했다. 보고서는 작업별 `playwright-report-desktop` / `playwright-report-mobile` artifact에 보관한다.

## 발견 및 수정

1. **모바일 화면 재방문 정지**: 모바일에서 등록되는 Service Worker가 Next RSC 응답까지 Cache First로 재사용했다. 재방문 시 HTTP 200을 받고도 로그인 화면이나 로딩 화면에 머물렀다. SW를 차단한 대조군에서만 정상인 것을 확인했다. 공개 아이콘만 캐시하고, 이전 SR 캐시만 제거하도록 변경했다. 로그인·업무 HTML의 오래된 오프라인 대체 화면은 제거되어 업무 화면 조회에는 네트워크가 필요하다.
2. **등록/상태 변경 창 잘림**: 320×568 사용자 등록 창이 화면 위아래를 벗어났다. 공통 Dialog와 AlertDialog에 동적 화면 높이 제한과 내부 스크롤을 추가했다.
3. **접수 전 고객 수정 실패**: 수정 창의 초기 고객사 설정을 실제 고객사 변경으로 오인해 기존 서비스 카테고리를 비웠다. 초기값을 유지하고 실제 선택 이벤트에서만 초기화한다. 고객이 변경할 수 없는 카테고리와 화면에 없는 우선순위 기본값을 보내지 않는다.
4. **고객에게 해결 내용 미표시**: 완료 처리에서 저장한 해결 내용이 상세 화면에 없었다. 완료·확인완료 상태의 상세 정보에 해결 내용을 표시한다.
5. **상세 화면 가로 확장·첨부 버튼 조작 실패**: 첨부·긴 상태 이력이 있는 393px 화면이 약 460px로 늘어나 삭제 버튼 클릭이 다른 요소에 가로막혔다. 그리드 축소 허용, 댓글·이력·탭 줄바꿈, 모바일 첨부 버튼 전용 행을 적용했다.
6. **접수 화면 긴 정보 배치**: 제목·파일명·이메일의 줄바꿈과 번호·우선순위·희망일의 줄 배치를 보완했다.
7. **WebKit에서 개발 화면 조작 불가**: HTTP 개발 서버의 자원을 CSP가 HTTPS로 전환해 CSS·JS 로딩이 실패했다. 개발 환경에서만 `upgrade-insecure-requests`를 제외했다. 운영 환경의 해당 정책은 유지하며 별도 회귀 테스트로 확인한다.
8. **WebKit 고객사 상세 가로 넘침**: 320px 화면의 탭 목록이 약 338px 너비로 배치되어 문서가 30px 확장됐다. 좁은 화면에서 헤더 작업 버튼을 분리하고 탭을 줄바꿈한다.
9. **WebKit 사용자 상세 가로 넘침**: 긴 이메일이 정보 칸을 벗어나 문서가 44px 확장됐다. 이메일에 긴 문자열 줄바꿈을 적용했다.
10. **알림이 모바일 업무 버튼의 터치를 차단**: 높이가 360px인 WebKit에서 상단 성공 알림이 ‘보류’ 버튼을 덮었고, 터치 위치에 따른 알림 타이머 일시 정지까지 겹쳤다. 알림을 하단으로 옮기고 빈 영역은 터치를 통과시키며, 항상 보이는 44px 닫기 버튼과 하단 안전 영역 여백을 적용했다.
11. **접수 중 입력한 작업 시간이 기본값으로 변경**: Chromium에서 8시간 입력이 SLA 기본값 72시간으로 저장됐다. 이전 초기 조회가 늦게 끝나면 작성값을 덮는 현상을 단위 테스트에서도 재현했다. 정리된 effect의 비동기 응답을 무시해 현재 입력을 유지한다. 회귀 테스트는 수정 전 `8→24`로 실패하고 수정 후 `8` 유지로 통과했다.

## 검증 한계와 다음 개선

- 브라우저 기기 에뮬레이션 결과다. 실제 Android/iPhone, OS 키보드, 카메라/사진 선택, 설치된 PWA, 네트워크 전환은 실기기에서 추가 확인해야 한다. 390×360 검사는 키보드 자체를 재현하지 않는다.
- 실제 가입 메일·푸시 발송, 운영 알림 재발송, 사용자 승인/비활성화·권한 변경·조직 이동·시스템 설정 저장은 수행하지 않았다. 해당 관리 화면은 조회·입력·취소까지 확인한다.
- 접수 달력·접수 정보 재수정·마감일 조정의 추가 시나리오는 두 브라우저의 주간 모드에서 검사한다. 그 외 핵심 SR 연속 시나리오는 주간·야간을 모두 포함한다.
- 댓글 실패 복구는 브라우저 fetch에 한 번의 503 응답을 주입한 검사다. 오류 문구·입력 유지·댓글 미저장·실제 재시도 성공을 확인한다. Service Worker는 계속 활성화하며 실제 통신사 네트워크 장애 재현과 구분한다.
